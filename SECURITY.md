# Security policy

SENTINEL is an early local development project and is not suitable for production monitoring. Do not expose its default HTTP listener beyond loopback, and do not submit sensitive telemetry.

Report suspected vulnerabilities privately to the repository owner through GitHub's security advisory feature. Include affected version, reproduction steps, and impact. Do not include live secrets or personal data in public issues.

Telemetry, endpoint, alert, incident, audit, and Sigma test endpoints require an administrator or analyst bearer token. The administrator token is generated per start unless `SENTINEL_ADMIN_TOKEN` is configured; `SENTINEL_ANALYST_TOKEN` optionally configures a separate analyst credential. Analyst credentials cannot reset simulations. This is a small configured role split, not user accounts or session-based authentication. Health, rule catalog, and scenario catalog endpoints are public. HTTPS can be enabled with certificate and key environment variables and enforces TLS 1.3. Setting `SENTINEL_CLIENT_CA` verifies any presented client cert; event ingestion then requires a verified cert whose URI SAN identifies the submitted `host_id`. Browser users can still access analyst routes with bearer auth. Certificate identities are provisioned out of band and cannot yet be rotated or individually revoked. The shared bearer token remains required. The Windows agent is read-only but has not been run on Windows 11 here. The agent and service redact common credential-named command-line arguments and custom field names before spooling or persistence; this is a narrow filter, and arbitrary secret formats may still appear in telemetry. Write endpoints use a process-local per-IP rate limit; it does not coordinate across replicas. There is no formal release signing, automated dependency scanning pipeline, or external security review. The simulator creates synthetic records and does not execute attack actions.

`POST /api/rules/test` evaluates one bounded Sigma YAML rule against one supplied normalized event. It does not persist the rule or apply it to ingestion. The current parser version identifies itself as draft-spec; this is not a claim of full Sigma compatibility.

## Redaction evidence

The Rust normalization test `command_line_secrets_are_redacted_before_spooling` verifies common `password`, `token`, and `api-key` argument forms before an event enters the durable outbox. The Go model test `TestRedactSensitiveRemovesCommonCommandLineCredentials` covers command-line and key-named custom fields, and `TestIngestAndAnalystWorkflow` verifies redaction occurs before backend persistence. The filter does not inspect arbitrary free text or guarantee that every credential format is recognized.
